## Context

当前 `wiki-local-repository-plugin` 主要提供 `analyze` 与 `get-latest`，工作流是“单次扫描 -> 读取结果”，缺少可中断的长任务控制与基于文档库持续问答。与此同时，插件系统已有运行时、权限门禁、画布钩子与宿主 API 门面，但缺少一套可复用的“插件任务控制 + 文档会话桥接”基础能力。该变更要在不破坏现有插件契约的前提下，把 DeepWiki 类能力沉淀为插件系统基础设施，并先由 Wiki 插件消费。

约束：
- 继续遵循本地优先（插件工作区持久化）与插件隔离边界。
- 复用现有 Agent 模块成熟模式（流式事件、会话状态、可中止流程），但保持插件系统抽象而非直接耦合 Agent 实现。
- UI 必须通过插件工作台统一壳层表达状态，避免 Wiki 插件自建一套异构交互。

## Goals / Non-Goals

**Goals:**
- 为插件系统增加统一的 AI 扫描与索引能力：仓库遍历后执行语义分块、Embedding 与检索索引构建，并落盘到插件工作区。
- 为插件系统增加统一的长任务控制能力：开始、暂停、继续、停止、状态查询与事件推送。
- 为插件系统增加统一的文档会话桥接能力：基于指定知识库上下文进行流式问答与多轮会话。
- 将扫描模型选择纳入插件调用参数与状态持久化，支持不同模型策略。
- 让 Wiki 插件形成闭环：仓库扫描（可控）-> 文档库构建 -> 基于文档库聊天。
- 更新插件规范文档，明确哪些能力收敛为宿主基础能力，哪些留在插件内部。

**Non-Goals:**
- 不在本次引入远程向量数据库或外部托管检索服务。
- 不重写 Agent 模块本身，不把插件会话直接并入 Agent 会话存储结构。
- 不为所有历史插件强制迁移到新协议；仅提供向后兼容适配层与渐进接入路径。

## Decisions

1. 引入插件级任务控制抽象（Plugin Task Runtime）
- 决策：在 `main/lib/plugins` 增加任务控制器，定义任务状态机（`idle/running/paused/stopped/completed/failed`）、任务句柄、控制命令与事件分发。
- 原因：暂停/继续/停止是跨插件共性需求，放在 Wiki 插件内会导致后续插件重复造轮子。
- 备选：
  - 仅在 Wiki 插件内部实现控制逻辑：短期快，但不可复用。
  - 直接复用后台任务 Hook 的 UI 状态：只能覆盖前端展示，无法形成主进程强一致控制语义。

2. 会话桥接采用“插件文档聊天服务”而非直连 Agent 内核
- 决策：在宿主侧提供独立的插件文档聊天桥接服务（输入：pluginId、knowledgeBaseId、model、messages；输出：流式事件），Wiki 插件通过 capability 调用。
- 原因：可复用于未来其他“文档问答类插件”，并保持与 Agent 模块低耦合。
- 备选：
  - 直接复用 Agent Session Manager：耦合过深，插件和 Agent 生命周期/权限语义不同。
  - 插件内部自行请求 LLM：重复鉴权与流式协议实现，难以统一可观测性与安全门禁。

3. 扫描与文档索引采用“AI 增强索引流水线”
- 决策：扫描任务不再停留于目录统计与纯 Markdown 摘要，而是输出结构化语义产物（文件树、代码分块、Embedding 向量索引、检索元数据）；聊天阶段优先消费已落盘索引，不直接依赖扫描进程内存。
- 原因：用户反馈现状“压根没用 AI 能力分析”，且 DeepWiki 参考项目已验证“分块+Embedding+检索”是文档库聊天可用性的前提。
- 备选：
  - 继续只生成 Markdown：实现成本低，但无法支撑高质量检索与多轮问答。
  - 在线即时检索源码：无需索引落盘，但延迟高、成本高、会话一致性差。

4. UI 协议扩展而非新增专用页面
- 决策：在现有 `plugin-ui-canvas-hook` 协议上扩展任务控制动作与聊天区块语义，由 `plugin-workbench-shell` 统一渲染。
- 原因：保持插件体验一致性，减少专用页面维护成本。
- 备选：
  - 新建 Wiki 独立页面：可快速实现，但破坏插件工作台一致性，难复用。

5. 模型选择作为任务与会话显式参数
- 决策：扫描模型与聊天模型均作为显式字段进入 capability 调用，并记录到插件工作区会话元数据。
- 原因：满足用户可选模型需求，便于后续回放与调试。
- 备选：
  - 仅使用全局默认模型：无法满足不同仓库规模/成本策略。

6. 文档规范同步更新策略
- 决策：在实现阶段同步更新 `PLUGIN.md` 与 `PLUGIN_WIKI.md`，将“插件系统基础能力”与“Wiki 插件业务能力”分层描述。
- 原因：避免规范与实现长期漂移，支持后续插件按统一范式接入。

## Risks / Trade-offs

- [暂停语义复杂] 任务可能处于不可中断阶段（例如单文件解析中） -> 采用协作式暂停点，定义“请求暂停”与“已暂停”两段状态并暴露进度。
- [流式事件风暴] 扫描与聊天并行时事件量大 -> 统一事件节流/批处理策略，渲染层按会话分桶订阅。
- [索引体积增长] 大仓库索引写入占用较多磁盘 -> 采用分片存储与保留策略（仅保留最近 N 次），并提供清理入口。
- [模型配置失配] 用户选择模型不可用或权限不足 -> 启动前做模型可用性校验并给出可诊断错误。
- [向后兼容成本] 老插件不支持新画布协议 -> 壳层提供默认降级渲染，不阻断旧插件使用。
