## Context

当前 Proma 的核心能力以内建服务为主，缺少稳定插件运行时边界，导致新功能扩展容易与宿主业务耦合。本次变更要求先解耦插件系统，再将 Wiki 作为插件实现，并满足 V1 约束：仅本地代码库、仅本地安装来源、启用/禁用/卸载低感知（用户无明显重启体感）。

现有约束：
- Electron 主进程 + preload + renderer（Jotai）架构已稳定。
- 本地存储优先，配置文件优先，不引入本地数据库。
- 需要增量接入，避免影响现有 Chat/Agent 主流程。
- 参考来源是 `/Users/mr.j/Downloads/Proma`，但需要基于当前仓库结构重定义，而非直接复制实现。

## Goals / Non-Goals

**Goals:**
- 建立独立插件内核，完成插件系统与宿主业务解耦。
- 定义稳定宿主-插件契约（manifest、权限、能力注入、生命周期）。
- 提供本地插件管理闭环：安装、启用、禁用、卸载。
- 实现低感知热生命周期，不要求用户显式重启应用。
- 在插件系统上落地 Wiki 插件（仅本地仓库）作为首个验证样板。

**Non-Goals:**
- 不做插件市场、远程插件仓库与在线更新。
- 不做多进程沙箱隔离（V1 采用受控 API 边界 + 异常隔离）。
- 不做远程仓库接入与协作编辑（V1 仅本地代码库）。
- 不做完整签名信任链与企业级审批流程。

## Decisions

### 决策 1：采用“插件内核 + 业务插件”双层架构

- 插件内核负责：发现、校验、加载、生命周期、权限门禁、状态管理。
- Wiki 作为独立业务插件，仅通过插件 API 使用能力。
- 理由：保证平台层和业务层解耦，避免后续能力扩展继续污染宿主。
- 备选：把 Wiki 先做成宿主内建再抽离。
- 不选原因：二次迁移成本高，行为易漂移。

### 决策 2：manifest 版本化 + 能力/权限分离

- 引入 `manifestVersion` 与严格校验，核心字段：`id/name/version/entry/permissions/capabilities/compatibility`。
- `permissions` 用于安全边界，`capabilities` 用于功能声明和 UI 发现。
- 理由：安全控制与功能编排分责，后续演进更稳定。
- 备选：只保留 permissions。
- 不选原因：插件功能发现与权限耦合，不利于编排。

### 决策 3：热生命周期采用显式状态机

- 状态：`installed -> active/inactive -> error -> uninstalled`。
- 启用：加载入口并执行 `activate(context)`。
- 禁用：执行 `deactivate()`，中止任务，解绑 IPC 和监听器。
- 卸载：禁用后移除安装目录与索引元数据，做幂等清理。
- 理由：满足低感知启停要求，同时可测试、可观测。
- 备选：启停卸载要求重启生效。
- 不选原因：与用户体验目标冲突。

### 决策 4：插件 API 采用受控 Facade

- 仅暴露最小 API：`llm`、`fs`、`mcp`、`events/ui`。
- 插件不得直接访问宿主内部 service 实例。
- 理由：降低 API 破坏性变更风险，提升边界安全性。
- 备选：直接暴露宿主服务对象。
- 不选原因：高耦合且容易越权。

### 决策 5：本地安装优先，插件目录标准化

- 插件安装目录：`~/.proma/plugins/<plugin-id>/`。
- 插件运行工作区：`~/.proma/plugin-workspaces/<plugin-id>/`。
- 插件索引元数据持久化到配置文件（不引入数据库）。
- 理由：符合项目本地优先原则，部署与迁移简单。

### 决策 6：分阶段落地，降低回归风险

- Phase 1：内核与契约落地（无 Wiki 业务逻辑）。
- Phase 2：安装/启停/卸载全链路与 UI 状态接入。
- Phase 3：Wiki 插件接入并联调。
- Phase 4：清理临时兼容层并补充验证。
- 理由：控制变更半径，逐步验证。

## Risks / Trade-offs

- [热禁用不彻底导致资源泄漏] → 统一 `dispose` 清理协议，回收 AbortController/IPC/watcher。
- [权限门禁遗漏导致越权] → 默认拒绝（deny-by-default），按 manifest 精确授权并记录审计日志。
- [插件异常影响宿主稳定性] → 生命周期边界强制 try/catch，故障置 `error`，宿主不中断。
- [Wiki V1 范围膨胀] → 严格限定本地仓库 + 基础索引与生成链路。
- [参考实现带入历史耦合] → 仅借鉴设计思想，按当前仓库重新建模。

## Migration Plan

1. 在 `packages/shared` 增加插件契约类型、通道常量、manifest schema。
2. 在 `apps/electron/src/main` 增加插件内核模块并接入 IPC。
3. 在 `apps/electron/src/preload` 暴露插件管理 API。
4. 在 `apps/electron/src/renderer` 增加插件管理状态与入口。
5. 实现本地安装、启停、卸载链路与状态同步。
6. 实现 Wiki 插件（本地仓库索引/生成/展示）并完成联调。
7. 增加回归验证；若出现严重问题，可临时关闭插件入口开关回退。
