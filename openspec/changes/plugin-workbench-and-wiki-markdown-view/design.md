## Context

当前插件系统已具备主进程运行时能力（扫描、安装、启用/禁用/卸载、权限校验、能力调用、异常隔离），并且 Wiki 插件已经可以生成 Markdown 产物到插件工作区。

现状问题集中在 UI 层：
- 插件主要在设置页使用，缺少与 Chat/Agent 同级的工作流入口。
- 插件缺少统一的“右侧画布”承载能力，难以形成独立、连续的插件体验。
- 插件开发者复用宿主能力成本仍偏高，存在样板逻辑重复。
- 尚未形成“宿主基础组件 + 插件扩展内容”的统一 UI 契约。

约束条件：
- 不能退化现有权限模型、生命周期热管理和异常隔离能力。
- 插件 UI 体验需与宿主整体视觉和交互一致。
- 保持对已安装插件的兼容，未声明 UI 钩子的插件仍可被管理。

涉及主要模块：
- `apps/electron/src/renderer`（导航、Plugin 工作台、插件 atoms）
- `apps/electron/src/preload/index.ts`（插件工作台桥接 API）
- `apps/electron/src/main/ipc.ts` 与 `apps/electron/src/main/lib/plugins/*`（UI 钩子、能力聚合）
- `packages/shared/src/types/plugin.ts`（UI 契约与宿主 API 类型）
- `apps/electron/resources/plugins/wiki-local-repository-plugin/*`（Wiki 插件界面能力对接）
- `PLUGIN.md`（长期插件开发指南）

## Goals / Non-Goals

**Goals:**
- 在左侧导航引入与 Chat/Agent 同级的 `Plugin` 入口，并提供工作台壳层。
- 在 Plugin 工作台实现“左侧插件列表 + 右侧插件画布”的稳定交互结构。
- 定义插件可选“自定义 UI 画布钩子”契约，使插件可声明并渲染右侧界面。
- 提供简化后的宿主 API（能力调用、文件读取、事件/状态同步、内容渲染）以降低插件开发复杂度。
- 提供宿主基础 UI 组件与布局协议，确保插件界面在视觉与交互上保持一致。
- 让 Wiki 插件在右侧画布直接展示 `latest.md`，并承载分析/读取闭环。
- 将 `PLUGIN.md` 作为插件开发规范入口持续维护。

**Non-Goals:**
- 不在本次引入远程插件市场或在线安装来源。
- 不在本次引入插件“任意前端代码注入”执行模型（例如直接加载任意远程页面）。
- 不重构 Chat/Agent 现有业务流程，仅做导航并列与状态隔离接入。
- 不在本次实现 Wiki 文档在线编辑，仅保证可读、可刷新、可追踪最新产物。

## Decisions

### 1) Plugin 入口以“应用一级模式”落地，而非设置页扩展

**Decision**
- 在现有应用模式中增加 `plugin` 视图，左侧与 Chat/Agent 并列。
- Plugin 工作台作为独立主视图承载插件体验，设置页继续保留“管理属性”（安装/启停/卸载）能力。

**Rationale**
- 满足“插件工作流入口与 Chat/Agent 同级”的核心目标。
- 将“日常使用”与“管理配置”职责分离，提升可发现性与一致性。

**Alternatives considered**
- 仅在设置页增强插件面板：实现快，但无法形成独立工作台体验，否决。
- 新开独立窗口承载插件：隔离强，但交互割裂、维护成本高，否决。

### 2) 工作台采用“宿主壳层 + 插件内容”双层结构

**Decision**
- 宿主固定提供：插件列表区、状态栏、错误/空态容器、右侧画布框架。
- 插件在右侧画布中提供“内容定义”，由宿主渲染。

**Rationale**
- 把复杂通用能力内聚到宿主，插件聚焦业务内容。
- 宿主掌握状态与异常表达，保证产品一致性。

**Alternatives considered**
- 插件完全控制整个页面布局：灵活但破坏一致性，否决。
- 宿主只提供空白 iframe：隔离强但通信复杂、体验不统一，否决。

### 3) 自定义 UI 画布钩子采用“声明式契约”而非直接执行任意 UI 代码

**Decision**
- 在共享类型中引入 `plugin-ui-canvas-hook` 契约：插件返回声明式画布模型（布局、区块、动作、数据源）。
- 渲染层由宿主组件解释并渲染该模型，动作统一回流到宿主 API / capability 调用。

**Rationale**
- 避免在渲染进程执行插件任意前端代码带来的安全与维护风险。
- 通过声明式模型复用宿主组件，实现一致 UI 与可控演进。

**Alternatives considered**
- 插件提供 React 组件并在渲染层动态加载：耦合打包链路、稳定性风险高，否决。
- 插件提供远程 URL 页面：安全边界弱，且违背本地优先原则，否决。

### 4) 宿主 API 采用“聚合 facade”并与权限门禁对齐

**Decision**
- 通过 preload 暴露聚合 API（列表、状态、画布数据、动作调用、Markdown 读取）。
- 主进程统一校验插件状态与权限后执行，渲染进程不直接接触敏感能力。

**Rationale**
- 减少插件开发者在 IPC 细节上的负担。
- 保持现有 permission-gate 的单一鉴权入口，避免绕过。

**Alternatives considered**
- 渲染层直接组合多个 IPC 通道：简单但易散乱、重复和越权风险上升，否决。

### 5) 基础 UI 组件协议化，作为插件 UI 的默认构建块

**Decision**
- 宿主提供标准组件语义层（Page/Panel/Split、Card/Section、Toolbar、Loading/Empty/Error、Markdown Viewer）。
- 插件画布模型通过组件 key + props 使用这些能力，避免重复造轮子。

**Rationale**
- 统一视觉语言和交互反馈，降低插件 UI 设计门槛。
- 组件升级可被宿主集中维护，插件成本更低。

**Alternatives considered**
- 插件自行管理样式体系：短期灵活、长期一致性和维护性差，否决。

### 6) Wiki 插件作为首个完整落地样例

**Decision**
- Wiki 插件在工作台右侧提供“分析本地仓库 + 读取 latest.md + Markdown 展示”闭环。
- 继续复用现有产物路径（插件工作区内 `wiki/latest.md`），并在画布中显式展示最近结果。

**Rationale**
- 可直接复用已实现 capability 与产物模型，风险低、验证价值高。
- 为后续插件提供可参考的“最小可行 UI 钩子”范式。

**Alternatives considered**
- 先做通用框架不改 Wiki：可行但缺少端到端验证样例，否决。

## Risks / Trade-offs

- [Risk] 画布声明模型表达能力不足，难覆盖复杂插件需求 → Mitigation：为模型做版本化设计，优先满足 80% 场景，并提供可扩展字段。
- [Risk] Plugin 模式引入后与 Chat/Agent 状态串扰 → Mitigation：使用独立 atoms 与模式边界，切换仅变更视图，不重置其他模式状态。
- [Risk] 大 Markdown 渲染导致右侧卡顿 → Mitigation：采用宿主 Markdown Viewer 的增量渲染/虚拟化策略并限制首屏加载量。
- [Risk] 插件异常影响宿主视图稳定性 → Mitigation：主进程调用保持异常隔离，渲染层统一错误边界与降级 UI。
- [Risk] 老插件未实现 UI 钩子出现“空白体验” → Mitigation：提供默认占位画布（能力列表 + 状态提示 + 跳转设置页）。
- [Risk] 宿主组件协议扩展过快导致插件适配成本上升 → Mitigation：组件协议语义化与向后兼容字段策略，变更写入 `PLUGIN.md`。

## Migration Plan

1. 扩展共享类型：补齐插件画布钩子、宿主 API、基础组件协议定义。
2. 主进程扩展插件运行时与 IPC：增加画布元数据读取、动作调用入口、状态事件。
3. preload 暴露聚合 API：为渲染层提供类型安全的 plugin workbench facade。
4. 渲染层落地 Plugin 一级入口与工作台壳层（左列表 + 右画布）。
5. 接入宿主基础组件映射渲染，统一空态/加载态/错误态表达。
6. 升级 Wiki 插件：接入画布钩子并展示 `latest.md` 与操作闭环。
7. 兼容策略：未声明画布钩子的插件使用默认画布，不阻断现有启停管理。
8. 验证：执行类型检查与关键路径手测（启停、画布渲染、Markdown 展示、异常隔离）。

**Rollback strategy**
- 若工作台出现阻断问题，保留并优先使用设置页插件管理流程。
- 插件 UI 钩子异常时自动降级到默认画布，不影响插件生命周期操作。
- 保持现有 capability 调用接口不破坏，避免影响已安装插件核心功能。

## Open Questions

- 画布声明模型首版边界：是否需要在首版支持表单布局与多步骤流程，还是先覆盖信息展示 + 操作按钮？
- 插件列表排序策略：按安装时间、最近使用，还是固定优先级？
- Wiki 右侧是否需要“历史版本切换”入口，还是仅展示 latest 即可？
- 设置页插件管理与工作台插件列表的职责是否需要进一步合并（避免重复入口认知成本）？
- `PLUGIN.md` 的更新节奏是否采用“每次协议变更强制更新”并在 CI 增加检查？
